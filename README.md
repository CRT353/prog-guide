# 编程与架构入门指南

> 写给**不写代码、但要指挥代码**的人。
>
> 如果你的软件是 AI 帮你写的，你看得懂界面、跑得通命令，但一打开源码就发懵 ——
> 这份文档就是为你写的。它不教你背语法，它教你**看懂结构、问对问题、验证结果**。

---

## 一、这份文档解决什么问题

现在有一种很常见的处境：

- 想要一个工具 → 让 AI 写 → 它写出来了 → 能跑 → **但你不知道它到底做了什么**。
- 出问题时 → 让 AI 修 → 它说"改好了" → **你不知道该不该信**。
- 想加点功能 → **你不知道该提什么要求，也不知道怎么验收**。

这不是"不会编程"的问题，而是**缺少一张地图**。你要的不是会写代码，而是知道：

| 你需要的 | 对应章节 |
|---|---|
| 一个项目里该有什么、怎么管、怎么写文档 | 第一章 |
| 该用什么语言、这门语言擅长什么、坑在哪 | 第二章 |
| 代码为什么要分层、为什么拆成几个进程、怎么一眼看出结构 | 第三章 |
| 亲手练一遍，从"看懂"到"能验收" | 第四章 |

---

## 二、怎么读

三条路线，按你的时间选：

**路线 A：速查（每次 10 分钟）**
只读每节末尾的 **「一句话总结」**。全书一百多个小节，扫一遍就能建立基本语感。

**路线 B：通读（一个周末）**
按顺序读。第一章讲"怎么管"，第二章讲"用什么写"，第三章讲"怎么搭"，第四章动手。

**路线 C：带着问题查（最实用）**
遇到具体情况直接跳：
- "AI 说要用 TypeScript，那是什么？" → 2.3
- "它把代码拆成五个文件，合理吗？" → 3.3 / 3.4
- "主进程、渲染进程是什么鬼？" → 3.8
- "它提交了一堆东西，我该看哪个？" → 1.4 / 1.5
- "怎么判断 AI 是不是在编？" → 1.11
- "我想练手，从哪开始？" → 第四章

## 四、贯穿全书的写法约定

为了一致和好读，本书统一用这些约定：

| 约定 | 含义 |
|---|---|
| **类比开路** | 每个抽象概念先用生活里的东西打比方，再给正式说法 |
| **一句话总结** | 每节末尾一行，只读这行也能连成完整脉络 |
| **常见坑** | 标出真实项目里最容易出错的地方（多数来自真实事故，不是凭空想） |
| **术语翻译** | 术语第一次出现时用括号给大白话，例如"沙箱（关起来，不许碰你的硬盘）" |
| **命令与代码** | 一律用代码块，可直接复制执行 |
| **🧭 换口气** | 部分小节之间插入的轻松内容，用来平衡密度，可以跳过 |

**一条重要的写作纪律**：凡涉及"这么做对不对"的判断，尽量给出**可验证的依据** ——
一条能跑的命令、一个能看到的输出、一条能复查的记录。没有依据的断言，本书会明确写成
"一般认为""经验上"，而不是伪装成定论。

## 五、书里的例子从哪来

**本书的例子全部取自公开的知名开源项目**（例如 `torvalds/linux`、`microsoft/vscode`、
`redis/redis`、`expressjs/express`、`vuejs/core`、`sindresorhus/awesome` 这一类），
**不依赖任何人的本机环境**。

这样做有两个好处：

1. **出名**：你大概率听说过它们，读起来有真实感；
2. **可验证**（这点更重要）：它们全都 `git clone` 得下来、GitHub 上也看得到。
   所以书里凡是说"它是这么组织的""依赖方向是这样的"，你都能**自己核对一遍**，
   而不是只能相信作者。

> **一条贯穿全书的纪律**：凡是能让你自己验证的地方，就给一条命令；
> 凡是给不了命令的，就写明"一般认为"或"不确定"。
> 书中**刻意不写会漂移的数字**（星标数、贡献者数、文件个数、测试项数），
> 因为那些一定会过期 —— 需要时改用一条命令让你当场数出来。

## 七、版本与维护

- 本目录是一个**独立的 git 仓库**（远端 `CRT353/prog-guide`），
  有自己的提交历史与标签，与工作区里其它项目互不影响。
- 工作区仓库以 gitlink（内嵌仓库引用）方式记录"当前用本书的哪个提交"，
  因此**改本书要在本目录里提交**，在工作区根目录提交是无效的。
- 内容会随认知更新。若某节与你的实际经验冲突，以**能复现的证据**为准 ——
  欢迎推翻本书的说法，只要附上依据。
